AI Architecture Patterns

Catálogo de Patrones de Diseño GenAI

Un catálogo de los principales patrones arquitectónicos para sistemas generativos. Diseñado con un enfoque estricto en Trade-offs: saber cuándo NO usar un patrón es tan importante como saber implementarlo.

1. Provider Abstraction (Engines)

Problem: Atarse al SDK de OpenAI o Anthropic impide cambiar de modelo fácilmente.
Pattern: Crear una interfaz `ModelEngine` genérica. El resto del código llama a `generate(prompt)`, y por debajo, una implementación específica (ej. `OpenAIEngine`) traduce la solicitud.
When to use: Siempre. Es una buena práctica fundamental en sistemas de producción.
When NOT to use: En prototipos de 1 hora.
Trade-offs: Pierdes acceso rápido a características experimentales únicas de un proveedor (ej. funciones beta muy específicas) hasta que las abstraes.

2. Model Routing

Problem: Usar GPT-4 o Claude 3.5 Sonnet para cada tarea trivial arruina tu presupuesto y aumenta la latencia.
Pattern: Un Router evalúa la complejidad del prompt entrante y lo envía a un modelo "Barato/Rápido" (ej. Haiku/GPT-4o-mini) o a uno "Caro/Lento" (Opus/GPT-4o).
When to use: Cuando el sistema maneja millones de requests heterogéneos y el costo es una restricción severa.
When NOT to use: Si tu volumen es bajo, el costo de desarrollar el Router supera el ahorro en tokens.
Trade-offs: Introduce latencia inicial (el router toma tiempo en decidir). Si el router se equivoca, una tarea difícil se procesa con un modelo débil, devolviendo un error.

3. Retrieval / RAG (Context Boundary)

Problem: El modelo alucina porque no tiene acceso a datos privados o actualizados de la empresa.
Pattern: Inyectar una fase de búsqueda (Vector Database) ANTES de llamar al modelo. El resultado se añade al prompt como "Contexto".
When to use: Cuando los datos son demasiado grandes para caber en el contexto estático o cambian frecuentemente.
When NOT to use: Si tu manual solo tiene 30 páginas, mételo entero en el prompt. No diseñes RAG para datos estáticos pequeños.
Trade-offs: La calidad de respuesta queda atada a la calidad de la búsqueda (Si el motor de búsqueda falla, el LLM fallará). Costos de infraestructura por BBDD Vectorial.

4. Tool / MCP Boundary

Problem: Acoplar funciones locales a la lógica del Agente impide que el agente viva en la nube y los datos/APIs en infraestructura On-Premise.
Pattern: Separar las "Acciones" en un servidor independiente usando el protocolo MCP. El LLM decide "Qué hacer", pero el MCP Server decide "Cómo hacerlo y si tiene permisos".
When to use: Cuando necesitas ejecutar acciones en sistemas externos corporativos, o conectar el mismo set de Tools a múltiples agentes/IDEs (Problema N x M).
When NOT to use: Si solo necesitas una calculadora local o una herramienta trivial que vive en el mismo servidor web.
Trade-offs: Mayor complejidad de red (DNS, SSL, Autenticación entre cliente MCP y Servidor).

5. Evaluation Pipeline (Gatekeeper)

Problem: Actualizar un prompt rompe casos de uso que antes funcionaban (Regresiones silenciosas).
Pattern: Correr un "Golden Dataset" a través de una jerarquía de evaluación (Regex -> Semantic -> LLM Judge) antes de cualquier pase a producción.
When to use: Obligatorio para cualquier sistema GenAI desplegado a clientes reales.
When NOT to use: No hay excusa válida en producción, pero es excesivo para uso personal o scripts internos (Vibes-based evaluation es aceptable ahí).
Trade-offs: Mantener la rúbrica y los Golden Datasets es costoso. Riesgo de False Passes si el LLM-Judge es débil.
