LAB 06 · REAL ENGINEERING Module 06 · Agentic SWE · ⏱️ 90 min · Advanced · Protocol Design

AI generates candidates; the engineer owns the change. Este lab no trata sobre cómo usar un IDE con IA. Trata sobre cómo orquestar, validar y auditar una modificación de software cuando un modelo probabilístico está escribiendo el código.

01 —

Baseline Before AI

Antes de pedir a la IA que modifique una sola línea, debes conocer el estado exacto del sistema. Si los tests ya fallaban, necesitas saberlo para no atribuirle la regresión a la IA.

  • [ ] Current behavior (¿Qué hace ahora mismo?)
  • [ ] Current tests (¿Cuántos hay? ¿Están pasando?)
  • [ ] Current warnings/errors (Logs limpios o sucios)
  • [ ] Current git state (Workspace limpio, rama correcta)
02 —

Context Boundary Rule

No delegues a la IA la autoridad sobre la arquitectura. Tampoco asumas que un contexto mínimo es suficiente. Proporciónale el contexto relevante, declara tus supuestos y exige validación.

Ejemplo de prompt de control de alcance:

"Revisa estos archivos (Context). El objetivo es refactorizar X. Asumo que las dependencias están limitadas a Service Y y Utils Z. Identifica cualquier dependencia o contexto faltante antes de proponer la modificación de código."

03 —

Change Scope & Rollback

Debes delimitar explícitamente lo que está permitido y planificar el escenario de fallo, especialmente en sistemas legacy.

ALLOWED SCOPE
  • Archivos permitidos para modificar.
  • Comportamiento que DEBE mantenerse.
  • Criterio de aceptación técnica.
ROLLBACK PLAN
  • ¿Qué archivos están fuera de alcance?
  • ¿Cómo revertimos (git reset/checkout)?
  • ¿Qué pasa si fallan tests pre-existentes?
04 —

Human Review Checklist

Para combatir la ceguera por automatización (aprobar porque parece correcto), el equipo debe auditar el Diff generado respondiendo obligatoriamente a estos 9 puntos:

1. FUNCTIONAL: ¿Resuelve exactamente el issue original?
2. SCOPE: ¿Modificó solamente lo necesario o hizo refactor oculto?
3. BEHAVIOR: ¿Cambió comportamiento existente no relacionado?
4. DEPENDENCIES: ¿Introdujo nuevas dependencias o librerías?
5. SECURITY: ¿Introdujo una vulnerabilidad (inyecciones, logs sensibles)?
6. QUALITY: ¿El código sigue las convenciones y estilo del repo?
7. TESTS: ¿Los tests realmente demuestran que el cambio funciona?
8. MAINTAINABILITY: ¿Aumenta o reduce la complejidad ciclomática?
9. ROLLBACK: ¿Podemos revertirlo limpiamente si falla en CI/CD?
05 —

The Deliverable: EVIDENCE PACKAGE

Para este Lab, ejecuta un cambio real en un repositorio usando IA. Reúne los siguientes artefactos localmente para demostrar que auditaste el proceso completo:

  • Original Issue (Descripción del problema).
  • Context Manifest (Archivos inyectados).
  • AI Instruction (El prompt usado).
  • Generated Diff (El parche propuesto).
  • Test Results (Evidencia de ejecución pre y post).
  • Human Review (Checklist de 9 puntos respondido).
  • Final Decision (Accept/Reject y justificación).
