The Monolith Trap

El modelo es una dependencia, no la arquitectura

La evolución de la complejidad

A lo largo de Academy hemos visto cómo una simple llamada a un LLM (M01) creció hasta incorporar RAG, Tools, Agentes y Seguridad. El error de arquitectura más común en equipos nuevos es construir todo este sistema alrededor del SDK de un proveedor específico (ej. OpenAI Assistants API).

● Módulo 09: AI Architecture

El Problema del Acoplamiento

Todo mezclado

Model
 + Tools
 + Context
 + Retrieval
 + Evaluation
 + Security
 + UI
----------------
= EVERYTHING COUPLED

Cuando todas las capacidades están acopladas directamente al proveedor del modelo, el sistema se vuelve difícil de cambiar, difícil de testear y difícil de operar. Si sale un mejor modelo de la competencia, estás atrapado.

● Módulo 09: AI Architecture

El Modelo como Dependencia

Invirtiendo la jerarquía

Para construir sistemas resilientes, debemos invertir nuestra forma de pensar:

Mentalidad Principiante

"Mi aplicación es un wrapper alrededor de GPT-4."

Mentalidad Empresarial

"Mi aplicación tiene un motor de razonamiento intercambiable que actualmente usa GPT-4."

Separation of Concerns

Diseño basado en Componentes

🧩

La Plataforma Abstraída

Un sistema de IA moderno debe tratar al Modelo (LLM), la Memoria (RAG), la Acción (Tools) y la Seguridad (Evaluation) como servicios independientes con fronteras claras.

El Vendor Lock-in es solo una de las consecuencias negativas de no hacer esto. La imposibilidad de hacer Unit Tests y de escalar la plataforma es el verdadero asesino de proyectos.
