01 —

Retrieval es Generación de Candidatos, no Contexto Final

Existe el error conceptual de asumir que "hacer RAG es pegar los resultados de una base de datos vectorial directamente en el prompt". Retrieval no sustituye a Context Engineering. Retrieval es la etapa que recupera candidatos potenciales a escala masiva; luego esos candidatos deben evaluarse, filtrarse y ensamblarse:

Query → Retrieve Candidates → Evaluate Relevance → Select → Assemble → Validate → Useful Context
02 —

Selección de la Fuente de Conocimiento Real

Repositorio o Base de Datos Corporativa Masiva

Elige una fuente de conocimiento de tu organización donde la selección manual de archivos (M03) ya no sea viable:

  • Documentación de APIs internas o especificaciones Swagger/OpenAPI extensas.
  • Diccionario de datos o esquemas de base de datos relacionales con más de 100 tablas.
  • Manuales operativos, políticas normativas o contratos legales corporativos.
  • Historial anonimizado de incidentes técnicos o tickets de soporte.
03 —

Estrategia de Búsqueda: Más allá de los Embeddings

No todas las búsquedas requieren bases de datos vectoriales. Tu especificación debe justificar la combinación adecuada de técnicas:

LEXICAL SEARCH (BM25 / Full-Text)

Ideal para coincidencia exacta de nombres de funciones, IDs de error, tablas SQL y términos técnicos específicos.

SEMANTIC SEARCH (Embeddings)

Ideal para preguntas conceptuales en lenguaje natural donde el usuario no conoce la terminología exacta.

HYBRID SEARCH (Lexical + Vector)

Combina puntuación semántica y léxica para maximizar la cobertura sin perder precisión de términos.

METADATA FILTERING & RERANKING

Filtra candidatos por versión, fecha o permisos, y reordena con un Cross-Encoder para eliminar ruido (M03).

04 —

El Artefacto: Retrieval Specification (14 Secciones)

RETRIEVAL SPECIFICATION TEMPLATE CASE OS STANDARD
1. Knowledge Source: Fuente de datos y formato.
2. Retrieval Problem: Tipo de consultas y requerimiento.
3. Chunking Strategy: Tamaño (tokens), overlap y límites.
4. Metadata Strategy: Tags, módulos, timestamps, roles.
5. Search Strategy: Léxica, semántica o híbrida.
6. Top-K Policy: Justificación del umbral de candidatos.
7. Reranking Rules: Reglas de re-ordenamiento.
8. Evaluation Benchmark: Matriz de 5 queries.
9. Precision@K Target: % mínimo aceptable.
10. Recall / Hit Rate: % de cobertura requerido.
11. Failure Cases: Comportamiento ante no-match.
12. Context Integration: Filtros post-retrieval.
13. Security Constraints: Control de acceso por rol.
14. Acceptance Criteria: Umbral de pase.

El Corazón del Lab: Evaluation Benchmark (5 Queries)

Para demostrar que la estrategia funciona, debes ejecutar un benchmark de 5 consultas reales representando casos típicos, casos borde y casos sin respuesta:

Query Fuentes Esperadas Top-K Falsos Positivos Precision@K Hit Rate Decisión
Q1 (Típica) Doc-A, Doc-B K=3 1 66% 100% PASS
Q2 (Término exacto) SQL-Schema-User K=2 0 100% 100% PASS
Q3 (Sin respuesta) Ninguna (Out of scope) K=3 3 (Ruido) 0% 0% FAIL → Añadir Threshold
Q4 (Ambigua) Doc-C, Config-Env K=4 2 50% 100% RE-RANK REQUIRED
Q5 (Multi-modulo) Doc-A, Doc-D, Auth-Spec K=5 2 60% 100% PASS
