Tool Calling & Contracts

El modelo propone. El software ejecuta.

Desmitificando el "Uso de Herramientas"

Un error común es creer que el LLM mágicamente "ejecuta" código o hace peticiones HTTP a la web. En realidad, un LLM es solo un motor de texto. Nunca toca el mundo exterior.

🤝

El Contrato

Tool Calling (o Function Calling) es simplemente un acuerdo de comunicación estructurada entre el modelo probabilístico y tu código determinista.

  • Le pasas al LLM una lista de funciones que tu código puede hacer.
  • Si el LLM cree que necesita usar una, pausa la generación de texto y devuelve un JSON pidiendo ejecutarla.
  • Tu código recibe el JSON, lo valida, ejecuta la función real, y le devuelve el resultado al LLM.

El Flujo Operacional

Cómo se ve en la práctica

1. User Intent & Tool Schemas -> Model

El usuario pide: "¿Qué clima hace en Madrid?". Tú envías esto al LLM junto con la definición (JSON Schema) de la herramienta `getWeather(city)`.

↓
2. Tool Call Proposal -> Application

El LLM responde con un mensaje especial indicando: "Propongo llamar a getWeather con el parámetro city='Madrid'".

↓
3. Validation & Execution -> Observation

Tu aplicación (TypeScript/Python) intercepta esta propuesta, ejecuta la llamada HTTP a la API del clima, y devuelve la respuesta ("24 grados, soleado") al modelo.

Conexión con M02

JSON Schemas al rescate

¿Recuerdas cómo en el Módulo 02 forzábamos salidas estructuradas? Tool Calling es exactamente la misma tecnología aplicada a la invocación de funciones.

// Tool Definition Schema

{{ '{' }} "name": "sendEmail", "description": "Envía un correo electrónico. Úsalo cuando el usuario solicite notificar a alguien.", "parameters": {{ '{' }} "type": "object", "properties": {{ '{' }} "to": {{ '{' }} "type": "string", "description": "Email del destinatario" {{ '}' }}, "body": {{ '{' }} "type": "string", "description": "Cuerpo del mensaje" {{ '}' }} {{ '}' }}, "required": ["to", "body"] {{ '}' }} {{ '}' }}

El modelo usa este contrato para construir la propuesta. Si tu código necesita un `email` válido y el modelo propone un nombre, tu código debe capturar el error y devolverlo al modelo como observación.

El nacimiento del Agente

Un flujo de "Tool-Calling" simple ejecuta una herramienta y termina. Pero, ¿qué pasa si la tarea del usuario es compleja?

"Analiza las ventas de Q1 usando `getSales()`, luego busca la causa de la caída en el repositorio de conocimiento usando `searchKnowledge()`, y envía un reporte por correo usando `sendEmail()`".

Para lograr esto, necesitamos encadenar múltiples peticiones de Tool Calling de forma dinámica. Aquí es donde introducimos el Agent Loop.
